# Partner Onboarding Deployment Incident

Date: 2026-05-14

## Summary

`POST /api/v1/partners` initially failed in production with a generic `503 Configuration Error`, then later returned `404 Not Found` after Keycloak onboarding configuration was added. The endpoint became available only after deploying the newer API image that contained the partners feature.

Final state:

- API image: `chownrmrf/wrapsfer-api:8180142fc37f99b55a61b2980fa3b04b1ea4bac1`
- `partner-alpha` status: `Active`
- Partner route verification: unauthenticated `GET /api/v1/partners` returns `401`, confirming the route exists and is protected.

## Impact

- Owner-admin partner creation could not complete.
- `partner-alpha` was left in the database with `Provisioning` status and `IsActive=false` after an earlier failed create attempt.
- Keycloak realm `partner-alpha` existed, but the local partner record was not active.

## Root Causes

- The live API container was running an older image, `bd1dee8979b4907e5d5f78a2d823edfa973f8b20`, which did not include `PartnersController`.
- The production compose environment did not pass Keycloak partner onboarding settings into the API container.
- The Keycloak admin service client was missing or under-permissioned for realm management operations.
- The first failed create left `partner-alpha` stuck in `Provisioning`; the retry endpoint only accepts `Failed` records.

## Resolution

- Added partner onboarding environment keys locally to `.env.example`.
- Added API environment pass-through keys locally to `compose.prod.yaml`.
- Updated remote `.env`, `compose.prod.yaml`, and `compose.yaml` with the same Keycloak onboarding configuration shape.
- Created/configured Keycloak client `wrapsfer-admin` with service-account access.
- Assigned the service account the required management roles from the Keycloak `*-realm` management clients used by this deployment.
- Updated remote `.env` to deploy image tag `8180142fc37f99b55a61b2980fa3b04b1ea4bac1`.
- Ran the EF migration bundle from the newer image; it completed and reported the database was already up to date.
- Recreated the API container with the newer image.
- Activated the existing `partner-alpha` record through `PATCH /api/v1/partners/partner-alpha/active`.

## Verification

- API container was running the newer image:

```text
chownrmrf/wrapsfer-api:8180142fc37f99b55a61b2980fa3b04b1ea4bac1
```

- Startup logs showed Keycloak issuer preflight passed and background consumers started.
- Unauthenticated route probe returned `401`, not `404`.
- Database check showed:

```text
partner-alpha | Active | IsActive=true | LastProvisioningError empty
```

## Follow-Ups

- Fix the production migration container/image mismatch permanently so `docker compose up -d api` does not fail on the `migrate` dependency.
- Consider making stuck `Provisioning` partner records recoverable through a guarded retry or admin repair flow.
- Document the Keycloak service-account role model for this deployment, especially that it uses `master-realm` and per-realm `*-realm` clients instead of `realm-management`.
- Ensure CI/CD deploys the expected image tag whenever partner onboarding code changes are merged.
